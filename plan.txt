# CYBER BBS — Implementation Plan & Technical Specification

**Version:** 1.0 · **Target:** single-file HTML app · **Language of all UI/content:** English (US) · **Codename:** `cyber-bbs`

---

## 0. AGENT BRIEF — READ FIRST

You are an autonomous coding agent running on a **Windows** machine. Your job is to build **Cyber BBS**, a browser-based simulator of a 1990s dial-up Bulletin Board System that is *aesthetically faithful* and *functionally real* (live news, real file downloads, real repos, real photos).

**Operating rules:**

1. Implement **phase by phase** (§18). Do not start a phase before the previous phase's Definition of Done passes.
2. After each phase: run the app, execute the in-app `SELFTEST`, fix failures, write a short entry to `CHANGELOG.md`, and `git commit` with message `feat(P<n>): <summary>`.
3. **No frameworks, no bundlers, no npm install required for the core product.** Vanilla ES2020+, one `<script>`, one `<style>`.
4. **No runtime CDN dependencies.** Every asset (font, art, seed data) is embedded in the HTML or vendored locally.
5. Do not invent endpoints. Use §11 tables. If an endpoint fails at build time, probe it, document the result in `docs/ENDPOINTS.md`, and use the listed fallback.
6. Never emit placeholder features. If something cannot work offline, it must degrade to bundled seed content with an in-character notice (§13.5) — never a blank screen or a raw JS error.
7. Ask no clarifying questions unless a requirement is genuinely contradictory; otherwise choose the option most faithful to 1993–1996 BBS culture and log the decision in `docs/DECISIONS.md`.
8. All user-visible strings live in a single `STRINGS` dictionary (§5.4) so tone stays consistent.

---

## 1. PRODUCT VISION

**Cyber BBS** is a fictional-but-plausible 1995 multi-node BBS: 14.4k HST Dual Standard, USRobotics Courier, running on a 486DX2/66 in a basement, SysOp handle **DR. NOISE**. The user "dials in" from a simulated terminal, hears a synthesized modem handshake, hits an ANSI login screen, and lands in a classic hotkey menu system.

The twist: the doors are **real**. News is live RSS. The file base pulls real public-domain / open-license artifacts. The GitHub Vault browses real repositories. The Photo Grabber searches real image APIs and saves real files to disk. Weather is real. Everything is wrapped in CP437, scanlines, and 16 colors.

**Design pillars**

| Pillar | Meaning |
|---|---|
| Authenticity | 80×25, CP437, ANSI SGR, SAUCE-aware art, baud-paced output, type-ahead, `[Y/N]` prompts, no mouse required |
| Reality | Every "door" performs a genuine network operation or genuine local computation |
| Craft | CRT power-on, phosphor bloom, synthesized modem audio, hand-made ANSI logo, sound design |
| Resilience | Offline-first; the BBS is always callable, even with zero connectivity |
| Exclusivity | Feels like a private, members-only system: access levels, ratios, credits, validation, node status |

## 3. TARGET ENVIRONMENT & WINDOWS NOTES

- Save all source files as **UTF-8 without BOM**; `<meta charset="utf-8">` mandatory (CP437 is rendered from a font/atlas, not from the file encoding).
- `file://` origin sends `Origin: null`. Only APIs returning `Access-Control-Allow-Origin: *` will work directly; everything else routes through the proxy chain (§13).
- Chromium allows `localStorage` per-file on `file://`; Firefox too. If a browser blocks it, fall back to in-memory session state and show `SYSOP NOTICE: Persistent storage unavailable — running in VOLATILE mode.`
- Audio requires a user gesture: the boot screen's **"PRESS ANY KEY TO DIAL"** satisfies autoplay policy.
- Tier 1 run: double-click the HTML. Tier 1 alt run (better CORS behavior): serve the folder over `http://localhost` (see §20).

## 4. SESSION LIFECYCLE (THE SPINE)

```
POWER ON → CRT degauss/flash → BIOS-ish POST text → terminal ready
   → "PRESS ANY KEY TO DIAL"  (audio unlocked)
   → AT command line / dial dialog (number prefilled)
   → DIALING → dial tone → DTMF → ringback → carrier handshake → CONNECT 14400
   → banner ANSI (scrolling, baud-paced) → login
        ├─ existing handle → password → welcome back + last call stats
        └─ NEW → new user application → limited access (guest)
   → system news / bulletins (pausable)
   → MAIN MENU (hotkey shell)
        └─ doors: News · Files · Photos · GitHub · Messages · Games · ANSI · Texts · Weather
   → [X] LOGOFF → session stats ANSI → "Thanks for calling" → ATH → NO CARRIER
   → idle attract mode (ANSI slideshow + "CALL CYBER BBS" ad)
```

**State machine states (authoritative list):** `OFF, POST, READY, DIALING, HANDSHAKE, CONNECTED, BANNER, LOGIN, NEWUSER, BULLETINS, MAIN, DOOR_*, CHAT, LOGOFF, HANGUP, ATTRACT`.

Every state defines: `enter()`, `exit()`, `render()`, `handleKey()`, `timeout`, and allowed transitions. Illegal transitions must be impossible by construction (router validates against a transition table).

## 5. ARCHITECTURE

### 5.1 Module map (all inside one IIFE, namespaced)

| Module | Responsibility |
|---|---|
| `Kernel` | boot, RAF loop, module registry, error boundary, event bus |
| `Term` | 80×25 cell buffer, ANSI/CP437 parser, cursor, scroll regions, dirty tracking |
| `Render` | canvas glyph atlas, palette, CRT post-effects, scaling |
| `Input` | keyboard capture, type-ahead buffer, hotkey dispatch, paste, mobile shim |
| `Modem` | AT command emulation, dial state machine, handshake scheduler |
| `Audio` | Web Audio graph: tones, DTMF, noise, key clicks, bells, ANSI music |
| `Router` | screen/state machine, door stack, back/exit semantics |
| `Store` | localStorage schema, migrations, export/import |
| `Net` | fetch orchestration, proxy chain, cache, rate limits, retries, offline detection |
| `Parsers` | RSS/Atom/RDF, JSON APIs, SAUCE, README/markdown→text |
| `Xfer` | download pipeline, Blob assembly, Zmodem-style progress theater |
| `Ansi` | ANSI art loader/player, image→ANSI converter, art gallery |
| `Doors` | News, Files, Photos, GitHub, Messages, Games, Texts, Weather, OneLiners |
| `Session` | user record, access level, time bank, credits, ratio, stats |
| `SysOp` | hidden console: config, feeds, keys, seeds, diagnostics, `SELFTEST` |
| `A11y` | live-region mirror, reduced motion, contrast, mute |

### 5.2 Data flow

`Input → Router → Door → Net/Parsers → Store(cache) → Term(buffer) → Render(canvas)`
Doors never touch the DOM directly; they emit terminal writes. This guarantees visual consistency and makes the whole app screen-reader-mirrorable.

### 5.3 Rendering strategy (mandatory)

- Logical grid **80×25**, cell **8×16 px** → 640×400 backing surface, integer-scaled (2× default) with letterboxing to preserve 4:3.
- Pre-render a **glyph atlas**: all 256 CP437 glyphs × 16 fg × 16 bg is too large → render glyphs in white to an offscreen atlas once, then tint per cell via a second pass or per-color cached atlases (16 atlases, one per fg color). Background painted as rects.
- Cell record: `{char, fg, bg, bold, blink, underline, reverse}`. Dirty-cell redraw only.
- Optional **80×50** mode for the ANSI gallery (8×8 font) and **132×37** "wide" mode for file listings if trivially supported.
- Font: **Px437 IBM VGA 8×16** (int10h Oldschool PC Fonts, CC BY-SA 4.0) embedded as base64 WOFF2; attribution in `LICENSE-THIRD-PARTY.md` and in the in-app `[I] About` screen. Fallback: `monospace` with a warning in SysOp console. Await `document.fonts.ready` before building the atlas.

### 5.4 Strings & tone

Single `STRINGS` object. Voice: terse, technical, slightly cocky SysOp. Use period-appropriate vocabulary: *node, baud, credits, ratio, leech, echomail, netmail, door, RIP, ANSI, sysop, validation, one-liner, TW2002*. Never modern SaaS language (no "dashboard", "onboarding", "Oops!").

## 6. TERMINAL ENGINE SPEC

### 6.1 ANSI subset to implement (T-01…T-14)

| ID | Sequence | Behavior |
|---|---|---|
| T-01 | `ESC[{n}m` SGR | 0 reset, 1 bold/bright fg, 4 underline, 5 blink, 7 reverse, 22/24/25/27 off |
| T-02 | SGR 30–37 / 40–47 | standard palette (§8.1) |
| T-03 | SGR 90–97 / 100–107 | bright palette |
| T-04 | SGR 38;5;n / 48;5;n | xterm-256 (map nearest to 16 unless HiColor mode) |
| T-05 | SGR 38;2;r;g;b | 24-bit, only when HiColor enabled (Photo door) |
| T-06 | `ESC[{r};{c}H` / `f` | absolute cursor addressing (1-based, clamped) |
| T-07 | `ESC[{n}A/B/C/D` | relative cursor moves |
| T-08 | `ESC[{n}J` | erase display 0/1/2 |
| T-09 | `ESC[{n}K` | erase line 0/1/2 |
| T-10 | `ESC[s` / `ESC[u` | save/restore cursor |
| T-11 | `ESC[{t};{b}r` | scroll region |
| T-12 | `ESC[6n` | cursor position report into input buffer |
| T-13 | `ESC[?7h/l` | autowrap on/off |
| T-14 | iCE colors (`ESC[?33h/l` or SAUCE flag) | disable blink → enable bright backgrounds |

Also: `CR`, `LF`, `BS`, `TAB` (8), `BEL` (audio beep), `0x1A` EOF truncation, and C1/unknown sequences swallowed silently (never printed as garbage).

### 6.2 Output pacing

- `bps` setting → `cps = bps / 10`. Profiles in §7.4.
- Default **Nostalgic mode = 2400 bps (240 cps)** for readable streaming; **Authentic mode** = negotiated rate with instant full-screen ANSI dumps (real BBSs at 14.4k felt instant).
- Chunked writes via RAF budget, never `setTimeout` per char.
- **Type-ahead buffer** (64 chars) accepted during output — authentic and important for usability.
- `ESC` or `Space` skips pacing for the current screen ("abort output" is a real BBS behavior).
- `[K]ontinue, [N]onstop, [Q]uit?` pager on any list > 22 lines.

### 6.3 Line noise

Injectable garbage characters + `NO CARRIER` events at a configurable rate (default **off**; SysOp toggle "Line noise: 0–5%"). Must never corrupt state, only visuals.

## 7. MODEM & AUDIO SPEC

### 7.1 AT command emulation

Support: `AT`, `ATE0/1`, `ATV0/1`, `ATZ`, `ATH`, `ATDT<number>`, `ATDP<number>`, `ATS0=n`, `AT&F`, `+++` escape, `ATO`. Unknown commands → `ERROR`. Responses: `OK`, `CONNECT <rate>`, `NO CARRIER`, `BUSY`, `NO DIALTONE`, `RING`.

Default dial number: **`+1 (555) 019-2847`** (fictional). A "phone book" lets users add entries; each entry can carry a **theme** (different ANSI banner + SysOp handle) — cheap, high-delight feature.

### 7.2 Handshake timeline (default profile: V.32bis 14400)

| t (s) | Event | Synthesis |
|---|---|---|
| 0.0–1.2 | Dial tone | 350 Hz + 440 Hz sine, −12 dBFS |
| 1.2–2.1 | DTMF dialing | 7 digits, 70 ms on / 50 ms off, standard US pairs (697/770/852/941 × 1209/1336/1477) |
| 2.1–4.1 | Ringback (1 ring) | 440 + 480 Hz, 2 s on |
| 4.1–4.4 | Silence / pickup click | short filtered click |
| 4.4–7.0 | V.25 answer tone | 2100 Hz, 180° phase reversal every 450 ms |
| 7.0–8.2 | V.8 CM/JM chirps | V.21 FSK 1650/1850 Hz, 300 baud, alternating bursts |
| 8.2–9.4 | Line probing (L1/L2) | tone ladder 150–3750 Hz, 150 Hz steps, 40 ms each |
| 9.4–11.6 | Training / scrambling | band-limited white noise 300–3400 Hz, amplitude LFO, 3 bursts |
| 11.6–12.4 | Ranging + final tones | descending sine sweep + short noise tail |
| 12.4–12.8 | Silence | — |
| 12.8 | `CONNECT 14400/ARQ/V42B/NONE` | typed at negotiated cps, then banner |

**Total ≈ 13 s.** Provide `Quick connect` (3 s compressed version) and `Silent dial`. `ESC` at any time → immediate `CONNECT` (skip). All timing values must be data-driven from a profile table, not hardcoded inline.

### 7.3 Audio graph & sound inventory

Master gain → soft clipper (WaveShaper) → 300–3400 Hz bandpass ("telephone") → destination. Separate bypass bus for UI sounds.

| Sound | Trigger | Method |
|---|---|---|
| Key click | keypress | 4 ms noise burst + 1.8 kHz ping, −28 dB |
| Terminal beep | `BEL` | 880 Hz square, 90 ms |
| SysOp page | `[C]` chat | 3 ascending bells, repeating until answered/timeout |
| Carrier loss | hangup | noise burst + descending tone + relay click |
| Transfer tick | Zmodem theater | 30 ms tick every 8 blocks |
| Error buzz | invalid input | 120 Hz square, 120 ms |
| ANSI music | ANSI art with music codes | square/tri oscillator, note table, optional |
| CRT power on | boot | 60 Hz thump + 15 kHz whine fade (respect mute) |

Global mute + volume in Settings; persisted.

### 7.4 Modem profiles

| Profile | Connect string | Handshake length | Display cps (Authentic) |
|---|---|---|---|
| Bell 103 | `CONNECT 300` | 5 s (simpler tones) | 30 |
| V.22 | `CONNECT 1200` | 7 s | 120 |
| V.22bis | `CONNECT 2400` | 8 s | 240 |
| V.32 | `CONNECT 9600/ARQ` | 11 s | 960 |
| **V.32bis (default)** | `CONNECT 14400/ARQ/V42B` | 13 s | 1440 |
| V.34 | `CONNECT 28800/ARQ/V42B/LAPM` | 15 s | 2880 |
| V.34+ | `CONNECT 33600` | 16 s | 3360 |
| V.90 | `CONNECT 56000/V90` | 19 s (adds digital "bong") | 5600 |

### 8.2 CRT effects (all toggleable, layered, GPU-cheap)

- Scanlines (CSS repeating gradient, 2 px period, 12% opacity)

- Flicker (0.6% luminance oscillation, 55 Hz — **disabled** under `prefers-reduced-motion`)

- Power-on: white horizontal line expands vertically, 380 ms, with degauss wobble
- Themes: `Color CRT` (default), `Amber Mono`, `Green Mono`, `Paper White`, `Flat LCD` (no effects)

### 8.3 Chrome

Terminal fills the viewport inside a black bezel. Optional **status strip** rendered *inside* the 80×25 grid (line 25): `NODE 1 · 14400 ARQ · NET:ON · 28:41 · CR:1240`. No modern UI widgets anywhere except the hidden SysOp console and file pickers.

## 10. SESSION, IDENTITY, ECONOMY

### 10.1 New user application (authentic friction, short)

Fields: Handle (2–16 chars, unique), Password (min 4, SHA-256+salt via SubtleCrypto, **local only**), Real name (optional, "or alias"), City/Location, Terminal type (`ANSI` / `TTY` / `AVATAR`→ANSI), Screen size (`80x25` default), Transfer protocol (`ZMODEM` default), "Who referred you?" (free text), and one validation question ("What does BBS stand for?" — any non-empty answer accepted, SysOp humor in response).

Then: `Application queued for SysOp validation.` Guest access **level 10** (browse + news + texts + ANSI). After the user downloads/uploads anything or plays a door once, auto-"validate" to **level 100 MEMBER** with an in-character netmail from DR. NOISE. This gives progression without blocking usability.

### 10.2 Access levels

| Level | Name | Rights |
|---|---|---|
| 0 | NEW | login only |
| 10 | GUEST | news, texts, ANSI, weather, one-liners (read) |
| 100 | MEMBER | + downloads (ratio), messages, games, photos, GitHub |
| 200 | CO-SYSOP | + no ratio, extended time |
| 255 | SYSOP | everything, console, unlimited time |

### 10.3 Time bank & ratio

- Daily time: **30 min** (MEMBER), 60 (CO-SYSOP), unlimited (SYSOP). Resets on local date change. Warnings at 5:00 and 1:00, forced logoff at 0:00 with `TIME EXPIRED — CALL BACK TOMORROW`.
- Credits: start 500. Download cost = ceil(KB / 10) credits, min 1. Upload grants ceil(KB/5). Ratio target **1:3** (uploads:downloads by bytes) — enforced only after 5 downloads (avoid frustrating first run). "Leech alert" message when exceeded; SysOp console can grant credits.
- Tracked stats: calls, minutes online, downloads, uploads, bytes, messages posted, doors played, favorite door, longest session.

### 10.4 Settings screen ("User Defaults")

Toggles/values: baud profile, pacing mode, CRT theme, effects on/off, scanline intensity, sound volume/mute, key click, line noise %, HiColor photos, dithering, pager on/off, hotkey vs command-line mode, default download area, feeds subscription set, city for weather, timezone, reset progress, export/import save file (JSON download/upload).

**File record fields:** id, area, name (8.3-styled display name), real filename, size bytes, date, description (≤ 3 lines), source, url, license, downloads count, credits cost, `NFO` text optional.

**Seed catalog:** ≥ 40 real, verified, legally redistributable items resolved at build time and embedded (metadata only; bytes fetched on demand). Agent must HEAD-check each and drop dead entries into `docs/ENDPOINTS.md`.

**Download pipeline (Xfer):**
1. Confirm screen: name, size, cost, ratio impact, `[D]ownload [V]iew [C]ancel`.
2. Fetch with progress (ReadableStream when `Content-Length` present; else indeterminate).
3. Render **Zmodem theater**: `Receiving: FILENAME.ZIP · Blocks 128/512 · 14,204 cps · ETA 00:07 · Errors 0` with `▓░` bar, occasional `NAK/Retry` flavor (cosmetic only, never fake failure).
4. Save via Blob + `<a download>`; also offer `[V]iew` for text/ANSI/NFO.
5. Log to download history, decrement credits, increment counters, write a fake `FILE_ID.DIZ` entry into the session log.
6. On failure: in-character `TRANSFER ABORTED — CRC ERROR` + retry option + real reason in SysOp console only.

**Upload (real):** `[U]pload` opens file picker → store bytes+metadata locally → grant credits → appears in area 07 → re-downloadable. This makes the ratio economy genuinely functional.

**Viewers:** `.txt/.nfo/.diz` → CP437 text viewer with pager; `.ans` → ANSI player (§11.7); images → ANSI preview (§11.3); anything else → hex-dump preview (first 512 bytes, authentic `DEBUG`-style) + save.

**Sources (in priority order):**

| Provider | Endpoint | Key? |
|---|---|---|
| Wikimedia Commons | `https://commons.wikimedia.org/w/api.php?action=query&generator=search&gsrsearch=<q>&gsrnamespace=6&prop=imageinfo&iiprop=url|size|extmetadata&format=json&origin=*` | no |
| NASA Images | `https://images-api.nasa.gov/search?q=<q>&media_type=image` | no |

| Lorem Picsum | `https://picsum.photos/seed/<q>/640/480` | no |
| **Google Images (optional)** | `https://www.googleapis.com/customsearch/v1?key=<K>&cx=<CX>&searchType=image&safe=active&q=<q>` | **BYO key + CSE id** |

**Policy:** Do **not** scrape Google Images HTML (ToS violation, brittle). The Google option is an official Programmable Search JSON API, disabled until the user pastes a key + CX in the SysOp console, with an on-screen note about the 100 queries/day free quota. Default provider = Wikimedia (CORS-friendly, permissive licenses, attribution shown).

**Flow:** query → 20 results as a numbered text list (title, dimensions, source, license) → select → **ANSI preview** → `[S]ave full image [T]humbnail ANSI save [O]pen original [N]ext`.

**Image→ANSI converter (spec):**
1. Draw to offscreen canvas at **80×50** pixels (or 160×100 in HiColor wide mode).
2. Optional Floyd–Steinberg dithering (toggle).
3. For each pair of vertical pixels, emit `▀` with fg = top pixel color, bg = bottom pixel color → 80×25 cells.
4. 16-color mode: nearest-color by weighted RGB distance (luma-weighted, tuned for VGA palette). HiColor mode: 24-bit SGR (T-05).
5. Respect aspect ratio with letterbox padding in black.
6. Cache previews (data URL key) in memory; save ANSI as `.ans` with a proper SAUCE record.

This is the single highest-wow feature — budget real time for it.

## 13. NETWORKING LAYER (`Net`)

### 13.1 Request pipeline

`request(sourceId, url, opts)` → check cache (fresh?) → if stale, serve stale + revalidate → build attempt chain → fetch with `AbortController` timeout **8 s** → validate status/content-type → parse → normalize → cache → return `{ok, data, meta:{source, cached, latency, via}}`.

### 13.2 Proxy fallback chain (for CORS-blocked sources)

1. **Direct** (only if source is marked CORS-safe)
2. `https://api.allorigins.win/raw?url=<enc>`
3. `https://corsproxy.io/?url=<enc>`
4. `https://api.codetabs.com/v1/proxy?quest=<enc>`
5. `https://r.jina.ai/<url>` (text extraction — good for article bodies)
6. **Tier 2 local helper** if running (§13.6)
7. Offline fallback (§13.5)

Mark each proxy's health with a rolling success score; reorder chain automatically; never retry more than **2** proxies per request; never send credentials through 2–5.

### 13.3 Politeness & limits

Per-host concurrency 2, global 4; min 400 ms between requests to the same host; exponential backoff (1 s, 3 s) on 429/5xx; honor `Retry-After`; hard session cap 300 requests; `NET` indicator flips to `OFF` after 3 consecutive total failures and auto-probes every 60 s.

### 13.4 Cache TTLs

| Data | TTL |
|---|---|
| RSS feeds | 15 min |
| Article body | 24 h |
| GitHub search | 10 min |
| GitHub repo/tree/README | 30 min |
| Image search | 30 min |
| Weather | 30 min |
| Archive metadata | 7 d |
| ANSI art bytes | 30 d |
| File bytes | never cached (stream to disk) |

### 13.5 In-character error copy (never expose stack traces)

| Condition | On-screen text |
|---|---|
| No connectivity | `*** NO CARRIER ON DATA LINK — SWITCHING TO LOCAL ARCHIVE ***` |
| All proxies failed | `*** NODE RELAY BUSY — TRY AGAIN IN A MOMENT (or press [L] for local cache) ***` |
| Rate limited | `*** UPSTREAM THROTTLED — QUOTA EXHAUSTED. WAIT 60s ***` |
| Parse failure | `*** PACKET CORRUPTED — CRC MISMATCH ON FEED <name> ***` |
| Empty result | `NO RECORDS FOUND. THE VOID ANSWERS NOT.` |
| Storage full | `*** DISK FULL — PURGING OLDEST CACHE SECTORS ***` |

Real diagnostics (URL, status, error) visible only in SysOp console `[N]et log`.

### 13.6 Tier 2 — optional local helper (do NOT make it required)

Deliver `tools/cyber-proxy.mjs`: a ~120-line Node 18+ single-file HTTP server on `127.0.0.1:8787` that (a) proxies GET with an allowlist of the hosts in §11, (b) adds CORS headers, (c) optionally saves downloads to `./DOWNLOADS/`. HTML auto-detects it (`GET /ping`, 500 ms timeout) and prefers it when present, showing `RELAY: LOCAL` in the status strip. No npm dependencies. Document startup in README. This solves every CORS/`file://` edge case for power users while keeping Tier 1 double-click viable.

## 14. SECURITY, PRIVACY, LEGAL

- **Sanitize everything remote:** parse HTML with `DOMParser`, extract `textContent`, strip control chars except ANSI in `.ans` files, cap lengths (title 200, body 20 000). ANSI parser must be bounds-safe (clamp cursor, cap params, reject > 16 params).
- No `innerHTML`, no `eval`, no inline event handlers from data.
- HTTPS only; reject `http://` URLs (proxy handles upgrade); block `javascript:`/`data:` in links.
- Add a restrictive CSP meta tag compatible with a single file (allow `'unsafe-inline'` for the inline script/style only if unavoidable; document the tradeoff).
- API keys: local only, masked in UI, explicit warning "stored in this browser, never transmitted except to the owning API".
- **Downloads:** only permissive/public-domain/CC-licensed or user-requested public artifacts. Show license + attribution on file detail and in the ANSI gallery. For abandonware on Internet Archive, link/stream user-initiated downloads only; no bulk mirroring; add a notice in About.
- **Google Images:** official CSE API only, SafeSearch on, quota notice; no scraping.
- **Fonts/art:** Px437 (CC BY-SA 4.0) attribution; each bundled ANSI keeps author/group/year from SAUCE; produce `LICENSE-THIRD-PARTY.md` and an in-app `[I] About → Credits` page.
- No personal data collection; "real name" field explicitly optional with alias hint.

# CYBER BBS — Complete Implementation Blueprint

**Project type:** Retro Bulletin Board System (BBS) simulator with real, usable web integrations  
**Primary entry point:** `index.html`  
**Target environment:** Modern desktop browsers, especially Chrome and Microsoft Edge on Windows 11  
**Interface language:** English only  
**Design direction:** Faithful 1990–1996 dial-up BBS atmosphere, presented as a polished modern website  
**Implementation approach:** Vanilla HTML, CSS, and JavaScript; no framework or build pipeline required for the core experience

---

## 1. Mission and Product Vision

Build **CYBER BBS**, a browser-based recreation of the experience of connecting to a computer Bulletin Board System (BBS) in the early-to-mid 1990s.

The experience should feel like a real BBS session rather than a modern website wearing a retro skin. Users should encounter a boot sequence, modem connection simulation, ANSI-style welcome screen, text menus, message areas, file areas, bulletins, a user directory, and classic door-style mini experiences.

Unlike a historical BBS, CYBER BBS must also be genuinely useful today. It should retrieve live news feeds, browse public GitHub repositories and releases, search openly licensed images, and download permitted files through the browser. It should combine the nostalgia of dial-up computing with real current Internet content.

The project should be original. Do not copy the branding, source code, artwork, or proprietary content of a specific historical BBS. Recreate common design conventions and interaction patterns from the era, while using original CYBER BBS branding and original text-based artwork.

### Core product principles

1. **Authentic first impression:** The first seconds should communicate dial-up BBS immediately: black screen, ANSI lettering, cursor, connection status, modem sounds, and a terminal-like layout.
2. **Real functionality:** News, repository information, image search, and browser downloads must use real external data rather than fabricated content.
3. **Terminal-first interaction:** Menus should support keyboard navigation and classic one-letter or numeric commands, not just mouse clicks.
4. **Honest simulation:** The modem sequence is an audiovisual simulation. The site does not place a telephone call, establish a modem connection, or communicate through a telephone line.
5. **Local-first persistence:** A visitor should be able to use the core BBS without creating an account. Preferences, local messages, bookmarks, and activity should persist in that browser.
6. **Safe external content:** Treat all feed items, repository descriptions, image metadata, and imported files as untrusted input.
7. **English-only interface:** All menus, labels, prompts, errors, help text, sample posts, and system messages must be written in English.

## 2. Scope and Important Technical Reality

### 2.1 What can be delivered as a static website

The primary application should be a static website whose entry point is `index.html`. It can be hosted on GitHub Pages, Cloudflare Pages, Netlify, or another static hosting service. It can also be run locally on Windows through a lightweight local HTTP server.

A static front end can provide:

- The full retro terminal interface and simulated dial-up session.
- Local user profiles and preferences.
- Local message boards, private notes, bookmarks, and activity history.
- Live access to third-party APIs that permit browser requests.
- Real browser-initiated downloads when the source permits them.
- Local file selection and browser-side import/export.
- Offline access to the shell and previously cached local content, if a service worker is added.

### 2.2 What a static HTML site cannot honestly provide by itself

A static site cannot securely provide a real shared multi-user BBS database, server-side accounts, cross-device message synchronization, private server-side mailboxes, or unrestricted RSS/API proxying. Those capabilities require a backend or serverless service.

The first release should therefore be a **single-user/local-first BBS with real live Internet integrations**. Local posts and user profiles are stored in the visitor's browser, not transmitted to a community server. The application must state this clearly in its help/about screen.

Design the data layer so a shared community backend can be added later without rewriting the terminal interface. Do not pretend that a locally stored post is visible to other visitors.

### 2.3 Recommended integration architecture

Use two deployment levels:

**Level A — Static-only core**

- `index.html` is the application entry point.
- CSS and JavaScript are separate assets for maintainability.
- Public APIs are called directly only where browser CORS permissions and provider terms allow it.
- Local data is stored in IndexedDB, with small preferences in localStorage.
- If a feed or provider blocks browser requests, show a useful explanation and an external link rather than silently failing.

**Level B — Optional lightweight integration proxy**

Add a small serverless proxy only when required for reliable RSS/API access. Suitable deployment targets include a Cloudflare Worker or a similar edge/serverless function.

The proxy must:

- Expose only specific, allowlisted integration routes.
- Never become an unrestricted URL-fetching proxy.
- Cache feed/API responses and enforce reasonable request limits.
- Keep API secrets in server-side environment variables, never in browser JavaScript.
- Reject private-network, localhost, link-local, and non-HTTP(S) destinations.
- Validate upstream response types and sizes.
- Return normalized data to the static front end.

Keep the serverless layer optional. The project must still boot and display a useful local BBS shell when no proxy is configured.

## 3. Historical BBS Experience to Recreate

The following features represent common BBS conventions from the era. Implement them as a coherent experience, not as a collection of unrelated widgets.

### 3.1 Startup and modem connection

Create a dedicated connection sequence that feels like dialing a remote computer:

1. Black screen and blinking cursor.
2. Short system initialization / terminal startup text.
3. `INITIALIZING MODEM...`
4. `DIALING CYBER BBS...`
5. Simulated ringing or line-wait phase.
6. Carrier detection and modem negotiation animation.
7. `CONNECT 33600` or another historically plausible displayed speed.
8. `CONNECTING TO REMOTE SYSTEM...`
9. CYBER BBS welcome screen.

The connection speed may be selected from a small historically plausible set such as 14,400, 28,800, 33,600, or 56K. It is a display effect only; do not imply that the browser is transferring data at a modem's actual bit rate.

The connection sequence must include:

- A visible progress indicator and short terminal status messages.
- A Skip button for visitors who do not want to wait.
- A Disconnect / Hang Up command.
- A clearly labeled `SIMULATED MODEM SESSION` status.
- A mute toggle and volume control.
- A setting to disable animation and sound.

The visitor must explicitly click **CONNECT** or another clearly labeled user gesture before audio begins. Browsers commonly block unsolicited audio playback; initialize or resume audio only after user interaction.

### 3.2 Modem sound design

Create an original dial-up-inspired sound sequence. Prefer procedurally generated tones using the Web Audio API, or original sound assets with documented usage rights.

The sound sequence can include:

- Dial tone-like opening tone.
- Touch-tone dialing pulses.
- Ringback-like pauses.
- Carrier squeal / handshake-inspired tones.
- Brief static/noise texture during negotiation.
- A short connection confirmation beep.

Requirements:

- Do not autoplay audio on page load.
- Start audio only after an explicit user action.
- Provide mute, volume, and sound-off-by-default settings.
- Stop all audio immediately on Hang Up, navigation away from the connection stage, or when the user disables sound.
- Avoid painfully loud, piercing, or excessively long sounds.
- Never use an unlicensed recording of an existing modem sound effect.

### 3.3 ANSI/terminal visual identity

The main application should resemble an 80-column BBS terminal while remaining usable on modern screens.

Visual direction:

- Very dark background, primarily black or near-black.
- Phosphor green as the signature CYBER BBS color.
- Optional amber, cyan, white, and dim green for hierarchy.
- Monospaced typography; use a readable bundled or system monospace fallback.
- ASCII/ANSI-style borders, separators, box drawing, and text banners.
- A visible block or underline cursor where appropriate.
- Subtle scanlines and CRT glow as optional effects, not mandatory overlays.
- Minimal gradients, rounded cards, shadows, or contemporary dashboard conventions.
- Small system/status line showing connection speed, current section, local time, and user/guest name.

The terminal should use a consistent 80-column-inspired grid on desktop. On small screens, reflow menus and wrap text intelligently rather than forcing unusable horizontal scrolling. Keep an optional `Compact Terminal` mode for mobile.

Offer visual settings:

- Green phosphor (default).
- Amber monochrome.
- White monochrome.
- High-contrast accessibility mode.
- CRT effects on/off.
- Reduced motion.
- Font size.

### 3.4 Login and user identity

Provide the following entry options:

- `GUEST LOGIN` — recommended default; no registration required.
- `NEW USER` — create a local browser profile.
- `RETURNING USER` — select a locally saved profile.

A local profile should contain:

- Handle / alias.
- Optional short signature.
- Join date.
- Last login date.
- Theme and sound preferences.
- Bookmarks and saved preferences.
- Local contribution/activity counters.

Explain that this profile exists only in the current browser unless a future shared backend is configured. Do not request a real-world name, address, phone number, or other unnecessary personal data.

### 3.5 Main menu

Create an ANSI-style main menu with numbered and lettered options. The menu should be recognizable as a BBS menu, for example:

- `N` — News & Bulletins
- `M` — Message Boards
- `E` — Electronic Mail
- `F` — File Areas
- `G` — GitHub Repository Library
- `I` — Image Library
- `D` — Door Games
- `U` — User Directory
- `H` — Help / Command List
- `S` — System Status
- `P` — Preferences
- `Q` — Log Off

Show the current section, user alias, session duration, simulated baud rate, and local clock in a compact status area.

The main menu must be navigable with:

- Keyboard letter commands.
- Number keys where appropriate.
- Arrow keys and Enter.
- Visible clickable menu entries for users who prefer a mouse or touch screen.
- A command prompt that accepts supported commands.

Unknown commands must return a friendly terminal response such as `UNKNOWN COMMAND — TYPE HELP FOR A LIST OF COMMANDS.`

## 6. Recommended Technical Design

### 6.1 Technology choices

Use:

- HTML5 for semantic structure.
- CSS for terminal layout, ANSI colors, responsive behavior, CRT effects, and themes.
- Modern vanilla JavaScript modules for behavior and integrations.
- IndexedDB for structured local data and optional local file blobs.
- localStorage for small preferences only.
- Fetch API for permitted external API access.
- DOMParser for RSS/Atom parsing, followed by strict safe text rendering.
- Web Audio API for original simulated modem tones.
- Blob/object URLs and normal browser download flows where appropriate.
- Service Worker only if offline caching is implemented and tested.

Avoid introducing a front-end framework unless the repository already requires one. The primary target is a lightweight, inspectable application that can run without a complex build system.

### 6.2 Suggested project layout

The implementation agent may adjust this layout if the existing repository has conventions, but keep the responsibilities separated:

- `index.html` — primary application entry point.
- `assets/css/` — terminal theme, layout, responsive styles, animation styles.
- `assets/js/app/` — application startup, navigation, state, command parser.
- `assets/js/ui/` — terminal renderer, menu, dialogs, notifications, keyboard handling.
- `assets/js/features/` — news, boards, mail, file areas, GitHub, images, doors, profile, status, settings.
- `assets/js/integrations/` — RSS, GitHub, Openverse, Wikimedia, optional proxy adapters.
- `assets/js/storage/` — IndexedDB schema, migrations, local preferences, import/export.
- `assets/data/` — built-in bulletins, sample boards, curated repositories, starter feeds.
- `assets/audio/` — only original/licensed assets, if audio files are used.
- `assets/images/` — original logo/artwork and local UI assets.
- `service-worker.js` — optional offline support.
- `serverless/` — optional proxy implementation, kept separate from the static front end.
- `README.md` — setup, local run, deployment, API configuration, limitations.
- `LICENSE` — project license chosen by the owner.

Do not put API secrets in any file that is deployed publicly.

### 6.3 State and navigation

Use a single application state model for:

- Current screen/section.
- Current profile and session state.
- Connection animation status.
- Theme, font, sound, and accessibility preferences.
- Selected board, message, feed, repository, file, or image.
- Current command input and history.
- Loading/error/cache state for integrations.

Keep feature modules independent of the visual renderer. For example, the GitHub module should return normalized repository/release records; the terminal UI decides how to display them.

### 6.4 Local storage model

Use IndexedDB for structured records such as:

- Local profiles.
- Boards and messages.
- Local mail.
- Read/unread markers.
- Bookmarks.
- Download history.
- Imported local files, if enabled.
- Cached feed items and API results.
- Door-game records and high scores.

Use localStorage only for small preferences such as theme, sound enabled/disabled, volume, and font size.

Add a database version and migration mechanism. Include `EXPORT MY DATA` and `RESET LOCAL DATA` actions. Ask for confirmation before clearing data. Explain that clearing browser site data may also remove locally stored BBS data.

### 6.5 Data normalization

Normalize external records before rendering. The user interface should not depend directly on provider-specific JSON/XML structures.

Create consistent internal record shapes for:

- News item.
- Repository.
- Release and release asset.
- Image result.
- File listing.
- Local message.
- Local profile.

Store provider/source identifiers and original URLs so users can trace content back to its source.

## 7. External Services and API Integration Plan

### 7.1 RSS/Atom feeds

- Maintain a configurable registry of feed URLs, titles, categories, and attribution labels.
- Validate the starter URLs during implementation.
- Support RSS 2.0 and common Atom formats.
- Parse titles, links, dates, descriptions, and source metadata.
- Limit the number of items stored per feed.
- Cache successful results and display the cached timestamp.
- Handle redirects, timeouts, malformed XML, network errors, and CORS failures.
- Do not display feed HTML as trusted application markup.

### 7.2 GitHub

- Use GitHub REST API endpoints for repository search/details and releases.
- Use public endpoints without a token for the static-first version.
- Cache and pace calls in accordance with GitHub's current limits.
- Prefer official release assets and source archive links.
- Display rate-limit or API-unavailable status in the UI.
- Do not scrape GitHub HTML pages to obtain structured data.

### 7.3 Openverse

- Use the Openverse API search endpoint for openly licensed media discovery.
- Preserve the returned creator, license, attribution, source page, and image URLs.
- Handle rate limits and API response changes.
- Verify the actual media license before presenting a result as reusable.

### 7.4 Wikimedia Commons

- Use Wikimedia Commons' supported search/API capabilities rather than scraping pages.
- Retrieve file metadata and license/author information where available.
- Link to the original Commons file description page.
- Respect Wikimedia API etiquette, attribution, and usage guidance.

### 7.5 NASA media

- Use official NASA RSS feeds and NASA media resources for space-related news and imagery.
- Check each item's credit line and NASA media usage guidance.
- Do not assume every image on a NASA page is automatically free of third-party restrictions.

### 7.6 Proxy configuration

If a proxy is implemented, provide a small configuration document explaining:

- Proxy base URL.
- Allowed upstream hosts/feed domains.
- Cache duration.
- Rate limits.
- Required environment variables.
- Deployment procedure.

If no proxy URL is configured, the app must continue in static-only mode.

## 8. Security, Privacy, and Content Safety

Security must be designed in, even though this is a nostalgic simulator.

### 8.1 Untrusted external content

Treat all external data as untrusted:

- RSS titles and descriptions.
- GitHub descriptions and release notes.
- Image titles, descriptions, creator names, and tags.
- User-entered board posts and mail.
- Uploaded local file names and metadata.

Render plain text safely. If Markdown rendering is used, sanitize it with a maintained sanitizer and disable unsafe HTML. Never inject untrusted HTML directly into the page.

### 8.2 URL validation

- Permit only `https:` external links by default.
- Reject `javascript:`, `data:`, `file:`, and unexpected schemes for navigation/download targets.
- Open external links in a new tab with appropriate opener protections.
- Do not blindly fetch arbitrary URLs supplied by a user.
- If a serverless proxy exists, enforce an explicit upstream host allowlist to prevent SSRF.

### 8.3 Secrets and authentication

- No API secret, private token, or server credential may be embedded in public JavaScript.
- Do not request a GitHub personal access token in the normal visitor workflow.
- If a future authenticated service is required, implement authentication server-side and document the security model.

### 8.4 Local data and privacy

- Clearly identify what is stored locally.
- Do not send local message-board content or profile data to external services.
- Provide export and reset controls.
- Avoid unnecessary personal information.
- Do not claim that local mail or posts are private against someone who has access to the same browser/device profile.

### 8.5 Downloads and uploads

- Do not auto-execute, auto-install, or auto-open downloaded files.
- Show source and file details before download.
- Apply size limits to locally imported files.
- Treat upload names and MIME types as untrusted.
- Keep local imports local unless a separate shared-backend upload system is deliberately implemented.

### 8.6 Accessibility and comfort

- Sound is opt-in and user-controlled.
- Provide a reduced-motion option.
- Avoid intense flashing or rapid strobing effects.
- Ensure adequate contrast and readable text sizes.
- All interactive features must be keyboard-operable.
- Provide visible focus indicators.

## 11. Testing and Acceptance Criteria

The implementation is not complete just because the screens look correct. Use the following acceptance tests.

### 11.1 Startup and connection

- Opening `index.html` through the documented local server shows the CYBER BBS landing screen.
- The CONNECT action starts the simulated connection sequence.
- The connection sequence can be skipped.
- Hang Up stops the sequence and returns to the landing screen.
- Audio does not play before the visitor clicks Connect.
- Sound can be muted at any time.
- The interface clearly states that the modem connection is simulated.

### 11.2 Terminal navigation

- Every main-menu item opens a working screen.
- Keyboard commands and visible menu controls both work.
- Unknown commands produce a helpful message.
- Escape/back navigation behaves consistently.
- No placeholder button is presented as functional.

### 11.3 Local data

- A local profile survives page reload.
- A local board post survives page reload.
- A reply remains linked to its parent message.
- Local mail can be composed, viewed, and deleted.
- Bookmarks and read states persist.
- Export produces a usable file.
- Reset asks for confirmation and removes only the intended local BBS data.

### 11.4 News

- At least two RSS/Atom sources are validated and load real recent entries.
- Publication dates are displayed correctly when present.
- External article links open the source website.
- A broken feed does not crash the app.
- Cached items remain accessible when a feed is temporarily unavailable.
- Feed descriptions are rendered safely as text.

### 11.5 GitHub

- Search returns real repositories.
- Repository details match GitHub data.
- Release information is shown when available.
- The app handles repositories without releases.
- The app handles `404`, rate limiting, and network errors.
- Download links point to official GitHub assets/source archives.
- No private token appears in browser source or network responses.

### 11.6 Images

- Search returns real provider results.
- Results show creator/source/license metadata where provided.
- Items without verified license metadata are labeled accordingly.
- The original source page can be opened.
- Direct download works only when the provider permits it.
- A failed image/API request does not break the terminal.
- Google Images is opened as an external search page only; no scraping is used.

### 11.7 Files

- File areas show real source information.
- A supported file can be downloaded through the browser.
- A blocked direct download falls back to the provider's official page.
- Transfer animation is labeled simulated.
- Local upload is visible only in the current browser and says so.
- The application never executes a downloaded or imported file.

### 11.8 Accessibility and compatibility

- Core navigation works without a mouse.
- Focus is visible.
- Sound can be disabled permanently in preferences.
- Reduced motion disables optional CRT/typing animations.
- Text remains readable on mobile.
- Chrome and Edge on Windows 11 complete the core flow without uncaught console errors.
